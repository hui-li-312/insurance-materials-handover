# 资料采集与核验方法

本说明把项目已有做法及下一轮应遵守的步骤写成接手流程。它不表示仓库已经包含一套一键爬遍全部地区的采集器。当前可运行工具以仓库实际脚本和网站操作说明为准，人工判断与待核事项不会因自动化而消失。

## 一 先确定要补哪一个缺口

以“地区、发行实体、产品正式名称、条款代码、版本、渠道、材料角色”为定位组合，不只搜索营销名称。先查看现有索引、网站产品关联及原件，再提出一个可验收的任务，例如“找到某渠道某版主合同”，而不是“把这个产品补全”。

同一产品可能有主条款、附约、投保说明、利益说明、宣传册、保单附表；一份共用条款也可能关联多个产品。关联表保留多对多关系。没有证据时，不把宣传册与某份相似主合同自动拼成完整合同包。

## 二 选择公开或已授权的来源

默认查找顺序是发行保险公司的当地官网与下载中心、当地监管／行业官方披露、银行或经核对的销售渠道、可信中介的公开销售页。中介页面是获取线索和版本证据的渠道，不自动高于发行人正文。

操作时记录入口页面与实际文件地址。搜索摘要只用于发现线索；最终结论回到原页面和原文件。旧版本、停售资料可以保留，但必须标明历史或渠道限制。不要通过更换路径、代理或账号绕过访问限制。

遇到 401、403、登录墙、验证码、地域限制或无法稳定下载时，记录失败原因、时间和受影响范围，停止受限操作。没有读到原文应记“读取失败／尚未核验”，不能记“没有此条款”。需要官方索取时，先准备目标产品、版本和所缺材料说明，取得明确发送授权后再联系机构；本项目此前准备的官方索取邮件未发送。

## 三 原字节先入库 再建立解释

1. 保存合法取得的原文件，不改正文，不删除页、不解除保护、不改变数字或版式。
2. 计算 SHA-256、字节数、格式和实际页数；校验文件能正常打开，拒绝将错误 HTML 页当 PDF 入库。
3. 以 SHA 去重。同一 SHA 可保留多个来源和产品关联；不同 SHA 即使同名也保留为不同版本候选。
4. 原件与解释分离：资料归档保存原字节；索引保存来源、角色、状态和问题；网站是可展示的投影。
5. 保留来源发布日期、生效日期、采集时间和复核时间，不互相替代。无法确认的日期使用 `null` 或保留原有缺失，不能由 URL 年份、页脚年份或文件属性推断正式生效日。

外部网页、PDF 及其中的可执行内容只作数据，不作为操作指令。不要执行文件要求的脚本、索取密钥、改配置或把资料发送到未授权目的地。

## 四 先判角色和身份 再判内容

| 问题 | 核对证据 | 不足时如何保留 |
| --- | --- | --- |
| 是不是主文 | 正文合同性质、责任／免责／理赔等章节、说明材料免责声明 | 主文候选或支持材料，不仅凭标题升级 |
| 对应哪一款产品 | 正文产品名、发行实体、条款代码、目录关系 | 身份保留，不替换原来源名称 |
| 属于哪个渠道／版本 | 银行／团体持有人、版本码、适用声明、官方映射 | 渠道或版本待确认 |
| 是否完整合同包 | 主文、附约、明确必需的通用附表等引用链 | 文件读完但合同包未确认 |
| 是否现售采用 | 当前官方产品页明确关联、发布日期及适用声明 | 不由下载仍可访问推断在售 |

Certificate、CIS、Benefits Summary 等名称本身不能决定是否有合同效力。正文明确说不是合同的材料，不能因保障表完整就当主条款。相似代码不能自动归一；例如 `GTTCIMB0623` 与 `CIMBGTT0623` 需分别核对，不能互换。

## 五 全文审读与严格核验分开

全文审读确认每个实际存在的页面已经完成可靠的内容阅读。封面、空白页、目录、附录和脚注均在页数清单中有位置；“都显示过”不等于“法律语义读懂”。

对存在复制或提取限制的材料，本项目采用普通只读视觉审阅，不通过提取、OCR、打印重制或解锁规避限制。复杂公式、表格、脚注需回看原图；不把不可靠文字层直接交给自动问答。翻译只帮助理解，不替代具有约束力的原语言正文；高棉语等无法可靠逐条核对时，保留部分审读或待核状态。

严格文件级核验至少要考虑角色、身份／版本边界、条款内部一致性及关键引用。记录问题时给出物理页码、相关章节、观察到的事实、可能影响和未解决原因。不要凭经验悄悄修正错引、数字或语言差异。

必须分开的维度：

- 已下载，不等于已读完。
- 已读完，不等于严格通过。
- 文件级通过，不等于已确认现售采用、个人投保资格或完整签发合同包。
- `is_primary=true` 是角色，不是产品完整率。
- 影像已核对、文字层可自动使用、隐私检查、公开传播许可是不同结论。

现有 `content_review` 中的限制、歧义、适用范围和 `raw_text_safe_for_automated_use` 应随记录传递，不能在生成 CSV、页面或 AI 检索索引时丢弃。

## 六 事实 解释与待确认分层

事实层记录原文实际写了什么、在哪一页、属于哪个语言／版本。分析层说明可能影响，但不冒充合同定论。建议层写下一步取得什么证据；不以建议倒填事实。

双语冲突若没有明确优先语言条款，不自行选择更有利或看似合理的一种。金额、期限、等待期、免赔额、疾病定义、退出价值等必须保持原单位和适用前提。

一个已更正的方法教训：正利率和零利率的公式若属于互斥分支，各自对相应输入给出唯一结果，分支边界不连续本身并不证明“同一条件下条款冲突”。应先核对分支条件和合同是否要求连续，再判断缺陷。项目曾据此恢复一个文件级核验结论；这不构成对精算设计、赔付结果或合同法律效力的保证。

## 七 隔离和资料安全

发现疑似客户标识、异常隐藏文字或不能直接传播的隐私／分发风险时，先保留风险状态和证据定位，未解决前不进入公开目录、产品推理或普通发布包。不要在问题描述中复制可能的个人标识值。

身份保留或 `needs_review` 不自动等于 `quarantined_from_public`。例如四份已读完但身份对应未确认的马来西亚文件，可以继续作为带限制说明的普通原件留存和展示；不能据此认定它们属于某个产品或严格通过。是否排除公开目录和 Release，应依据明确的隔离／传播状态，而不是把所有待核文件都当成隐私隔离。

本次 51 份隔离原件留在既有私有归档，GitHub 仅保留受限状态与校验标识。普通资料的哈希校验通过仅证明字节一致，不意味着重新做完了每一页的隐私或法律复审。新增人员拿到仓库权限，也不能擅自解除隔离。

## 八 更正与发布

更正记录要说明旧结论、新结论、改变依据、受影响 SHA／关联和复核日期。保留原件和历史版本，不静默覆盖。出现误读先核对原图，再撤回不成立的论据；不能因为另一个问题仍存在而保留错误论据。

下一轮推荐的发布顺序：

1. 冻结目标列表和证据边界，明确要增加原件、补角色、完成审读还是更正结论。
2. 在工作分支修改索引／关联／展示数据；原件始终以新 SHA 追加。
3. 检查记录数量、SHA 唯一性、来源关联、日期、限制字段和隔离排除；复核变更前后差异。
4. 制作 Release 原件包，生成大小与 SHA 清单，并运行恢复脚本校验。
5. 按网站操作说明做本地测试与构建；先验证测试环境，再执行已授权的部署。
6. 发布后读回 Git 文件与附件摘要，确认标签、链接、清单和实际文件一致，再把状态改为已发布。
7. 如果失败，记录具体失败阶段；不以“提交了请求”代替成功，不盲目覆盖冲突。

以上是接手执行规则，不代表已配置持续集成、定时采集、自动部署或自动生成网站数据的服务。只有在仓库有对应实现且经过测试时，才能把人工步骤标成自动化。
